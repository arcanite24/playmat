# Mana@Home S0: groundwork

S0 of [the design](Design.md): the pieces a worker needs before there's a coordinator, and the measurements that
decide how verification works.

## What S0 built

- **Answer logs** (`playmat-ai/src/answerlog.rs`). Every mulligan, bottom card and answer of a game, in order, as one
  line of text (`0m1 0b41 1B0 0O7 1A7.2 ...`) with its sha256. `Logged` records one around any decider; `Replayer`
  plays one back and stops at the first answer that doesn't fit.
- **Self-play as a library** (`playmat-ai/src/play.rs`). `pairing` (what a deal number decides), `play_game` (searches,
  training steps and the answer log) and `replay_game` (the same deal from its log, no search). The `selfplay` bin
  uses them and now also writes `wNN.answers.jsonl` beside each shard.
- **The protocol** (`playmat-swarm-proto`). `WorkUnit`, `ResultManifest`, `GameSummary`; `check_config`, the key
  allowlist that refuses `time_ms`, more than one thread per game, `vloss` outside GPU units and any network not named
  by the unit's sha256; `determinism_class`.
- **A local worker** (`playmat-worker`). `run-unit` plays a unit from a file, `verify` replays a result from its logs
  and checks it against the manifest, `compare` lines results of one unit up by answer-log hash, `class` names the
  machine's determinism class. It pins one search thread per game: `Config::default` otherwise takes up to 4, by the
  machine's cores.
- **The strict build** (`--features strict`). Matrix products run the packed 8-lane loop instead of `matrixmultiply`,
  and `exp`, `ln` and `tanh` come from the `libm` crate (`playmat-ai/src/fm.rs`).

## Browser worker (wasm32) scoping

- `cargo check --target wasm32-unknown-unknown -p playmat-ai` failed only on `EFFECT_MANA = 1 << 40`
  (`playmat-engine/src/rules.rs`), an ability-index tag that assumed a 64-bit `usize`. It is now `1 << 30` on 32-bit
  targets (64-bit builds are unchanged), and the engine, the AI and the protocol crate type-check for wasm32.
- What's left is at run time. `std::time::Instant::now` panics on `wasm32-unknown-unknown`, and `Table` calls it on
  every decision for its timing stats (`search.rs`, twice); it needs a clock shim (the `web-time` crate) before a game
  can run. The other calls sit behind `time_ms > 0`, more than one thread, or a `tcp://` network, which swarm units
  can't ask for.
- Threads: one single-threaded Web Worker per core, as the design says; nothing in a unit's game needs more.

## Measurements

All runs use the Phase 3 1.3M soup (`phase3-final-1.3m-v3-soup`, sha256 `6c9c9009…`) with the production learner
config (`ismcts`, `hide=1`, `samples=8`, `width=20`, `consider=14`, `belief_ms=1`, `temp=750`, `temp_turn=10` and the
rest), at `iters` 64 unless noted, on `constructed-2`, against itself (3 in 4) and `host@s6` (1 in 4), `keep` 200,
`fast ismcts:12`. Builds are from commit `7d541d6`. The audit's units and the six result manifests are in
[s0-audit.tar.gz](s0-audit.tar.gz): `playmat-worker compare r-audit-mac-strict r-audit-mv-strict` re-checks a row.

### Replay

| | |
| --- | --- |
| Answers per game | 310 (mulligans and bottom cards included) |
| Replay speed | 1,000 games (309,648 answers) in 8.7 s on one Mac thread: about 9 ms a game, 0.2% of the 4.3 s the game took to play |
| Tampering | A changed object choice, a truncated log and a wrong winner in the manifest each fail `verify` at the first bad entry. An answer the engine ignores and asks again (Java records those too) replays the same game, so changing one changes nothing a replay can see |
| Across classes | A result played by multivac's x86 strict build verifies on the Mac's default ARM build: replay runs no search, so it doesn't depend on the class |
| The refactor | `selfplay` at Phase 3 (`1e10fe5`) and at S0 write byte-identical shards for the same seed (20 of 20 files) |

### Determinism

"Alike" means the same answer log and the same training data (`log_sha256` and `steps_sha256`); jobs differed on
every host (Mac 4, multivac 10, blindvac 6).

| Comparison | Games alike |
| --- | --- |
| **Strict, 1,000-game audit: Mac (ARM macOS), multivac and blindvac (x86 Windows)** | **1,000 of 1,000 on all three: the S0 gate** |
| Strict at the production `iters` 384, Mac and multivac | 50 of 50 |
| Strict, Linux aarch64 (Docker on the Mac) and Linux x86_64 (WSL on multivac), against the Mac | 200 of 200 on both |
| Default, multivac and blindvac (one class: same exe, AVX2+FMA, same `ucrtbase.dll` 10.0.26100.9711) | 1,000 of 1,000 |
| Default, Mac against multivac (two classes) | 72 games diverge; of the 928 with the same answers, 926 differ in their training data |
| Default against strict, on the Mac | 85 diverge; all 915 others differ in their training data |
| The same Mac again, the audit's first 200 deals at `0ca49ee` (the lint fixes) with 2 jobs, default and strict | 200 of 200, both |

Across classes, about one game in twelve takes another move somewhere (`matrixmultiply`'s kernels round differently,
and one bit is enough for a search to pick another candidate), and nearly every game records different numbers: the
policy targets and q-values differ in their last bits even when every decision is the same. So answer-log hashes
alone can't check a re-run; the training data's hash has to match too, and re-runs only compare within a class. The
strict build makes every machine one class.

The training-data hash covers the steps as the search records them, in f32 and f64, before the shard rounds them to
f16. How many of those games still differ once stored is open for S1: if most match, a cross-class re-run could
compare stored shards and the answer log, and only the rest would need a re-run in their own class.

### Strict-math cost

| Host | Default | Strict | Cost |
| --- | --- | --- | --- |
| Mac (M-series, 1,000-game audits; 3 jobs default, 4 strict) | 10.2 ms an answer per thread | 13.8 ms | +35% |
| multivac (x86, 48-game bench, 2 jobs, quiet machine) | 17.4 ms | 22.4 ms | +28% |

Both are over the design's 25% line. The strict build became the default anyway (decided on 25 Nov): about 30% more
compute buys one class, so any account can re-run any other's unit. The first strict kernel cost 240% (one row at a time); blocking eight rows over the
packed weights brought it here. Tried and dropped: fused multiply-adds (slower in this loop) and an AVX copy of the
kernel (bit-identical, but no faster on a busy multivac). Timings on the Mac and multivac move by up to 2x with
their other work, so these are within a few points at best.

### Data per game

| | Raw | Gzipped |
| --- | --- | --- |
| Shard (18.6 recorded decisions a game at `keep` 200) | 62 KB | 2.9 KB |
| Answer log | 1.5 KB | 0.27 KB |

Entities (`ents.f16`) are 63% of the raw shard; most of it is padding, hence the ratio. The Phase 3 round
`phase3-r18-pfsp-gcp` had 22.9 recorded decisions a game, so these figures hold for real rounds. At the design's 13 games a
second the swarm would take in about 3.5 GB a day gzipped, which fits R2's free 10 GB as long as accepted rounds move
to Hugging Face.

## What S0 leaves for S1

- The strict build is the swarm's default (25 Nov). Units default to `strict`, the worker refuses a unit its build
  doesn't match, and CI runs the strict build's unit tests. The speed work left is the strict kernel itself: it is
  the plain loop over the packed weights, and a faster fixed-order kernel would pay back on every worker.
- `verify` checks every file's hash, every answer and the outcome, but not that the recorded steps match what the
  replay would record: that needs the replay to rebuild observations, which is the next step for the intake check.
- On Windows, the default build depended on `vcruntime140.dll` (blindvac lacked it); since S1, `rust/.cargo/config.toml` links the
  C runtime statically.
- The Steam Deck was off; Linux was measured after the gate in a container and in WSL instead (above).
