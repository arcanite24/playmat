# Mana@Home S1: private alpha

S1 of [the design](Design.md): a coordinator, a worker that plays units from it, and the gate, "a round trained only
on swarm data". S0's results are in [S0.md](S0.md).

## What S1 built

- **The coordinator** (`playmat-swarm`): axum and SQLite, metadata only. Shards go straight to R2 (or a local store)
  by presigned URL. It has role tokens (worker, trainer, admin) and leases with heartbeats. A host that fails a unit
  never gets it again, and `/release` hands back a unit the host stopped playing without counting a failure. When a
  round is published it rewrites the round's network URLs to its own public address.
- **The worker's run loop** (`playmat-worker run`): lowest priority, the idle rules from `fleet.py`, every option as
  `MANA_*`. A unit's thread shards are joined into one (`w.*`) before upload, so an upload is about 22 files at any
  thread count.
- **The trainer's side** (`rust/rl/swarm.py`, `pfsp_league.py --swarm`): publish a round, wait, pull every completed
  unit, replay it with `playmat-worker verify` against the unit the coordinator leased, and send the verdict.
- **Deployment** (`ops/swarm/`): https://mana.deimos.studio runs on the Hetzner box in `/srv/mana`, reached through a
  Cloudflare Tunnel, with intake in the R2 bucket `mana-intake`. The strict worker image builds from
  `Dockerfile.worker`.

## The gate round (2026-11-25 and 26)

| | |
| --- | --- |
| Learner | `phase3-final-1.3m-v3-soup` (the Phase 3 v3 soup of r16 to r18), ISMCTS at 384 iterations |
| Opponents | itself (weight 4), `phase3-r18-1.3m-v3` at 256 (weight 1), `host@s6` (weight 1) |
| Units | 24 of 100 games published, 19 played by the cutoff: 1,900 games |
| Workers | GCP Spot `c2d-highcpu-16` VMs (one at a time) and the Mac at 4 threads |
| Verdicts | 19 accepted, 0 rejected; every game replayed from its answer log (about 1 s per unit) |
| Training | `train.py --init` the soup, on those 19 units only: 69,181 decisions, 3 epochs, 93 s on the Mac (MPS) |
| Rating | a 400-game swarm round, new against init at 256 iterations: 201 won, 16 drawn, 183 lost |

The trained network scores 52.3% against its init, +16 Elo with a 95% interval of -18 to +49. One round of 1,900
games isn't meant to show a gain. The gate asks that a round's data come only from the swarm, pass replay, and train,
and this one did. Games the x86 EPYC VMs played replay exactly on the Mac's ARM, as `strict-1` promises.

What the round taught:

- **Upload limit.** A 16-thread worker wrote 20 files per thread, 320 in all, and the coordinator takes at most 64 per
  unit, so every unit of the first VM failed at upload. The worker now joins the thread shards (b9e3c85).
- **Speed.** With the strict build a game of this learner takes about 224 vCPU-seconds on a c2d VM, so 16 vCPUs play
  100 games in about 23 minutes. The Mac's cores take about 73 CPU-seconds a game.
- **Quota.** The GCP project allows 32 vCPUs in all regions together, whatever the regional quotas say, so only one
  16-vCPU VM fit beside other work. The round cost about $3 of Spot time.
- **Priority.** A later round can't jump the queue yet: the rating round's priority was raised by hand in the
  coordinator's database. The admin API needs a way to set a round's priority and to cancel units.

The swarm can play only Obs v3 networks. Phase 4 (Obs v4) isn't in this branch, so its learners can't go to the swarm
until the worker carries it.
