Run a server

A Playmat server is four containers started with Docker Compose: the XMage game server, Caddy serving the web client over HTTPS, a cache for card pictures, and a nightly backup. You don't build anything: the images are published for x86 and ARM.

What you need

  • A Linux machine with Docker Engine and the Compose plugin (docker compose version answers). Docker Desktop on a Mac or Windows works too, but the Update button needs Linux.
  • About 1 GB of memory for the server; 2 GB leaves room. One CPU is enough for a group's evening.
  • A domain name pointed at the machine, with ports 80 and 443 open, so Caddy can get a certificate. For a group on one home network you can do without one: see Private server on a LAN. Already running Traefik, nginx or another reverse proxy on 80 and 443? See Behind your own reverse proxy.

Install

# get the compose file and its settings
git clone https://github.com/arcanite24/playmat.git
cd playmat
cp ops/web/.env.example ops/web/.env

# edit ops/web/.env (below), then start it
docker compose -f ops/web/docker-compose.yml --env-file ops/web/.env up -d

The first start pulls the images and takes a minute or two. Then open https:// and your domain.

Settings to set first

All settings live in ops/web/.env; empty ones use the defaults. These are the ones to look at before the first start:

SettingWhat it does
DOMAINThe server's address, without https://. Required.
XMAGE_AUTHtrue makes players register with a password. Use it on any server others can reach; staff roles and Career need it.
XMAGE_OWNERThe account name of the server's owner. Register that name first: it gets the admin console, with every staff tool.
XMAGE_ADMIN_PASSWORDA break-glass password for the admin console, for when no owner can sign in. Leave it empty to turn that off.
XMAGE_SERVER_IMAGE, XMAGE_WEB_IMAGEThe images to run. The example file names the newest build of master; leave them as they are.

Mail (for password resets), Discord notifications, registration rules and the rest are in the settings table. After changing .env, run the same up -d again to apply it.

If the game server runs out of memory, it stops and Docker starts it again within seconds (games in progress end). To find out what filled it, set XMAGE_HEAP_DUMP=true: the next time it writes the memory to logs/heap-oom.hprof in the logs volume. XMAGE_MEMORY sets the memory size.

After the first start

  1. Open your domain and register the account named in XMAGE_OWNER. Until you do, the sign-in screen says the owner account doesn't exist yet. XMAGE_ADMIN_PASSWORD doesn't sign you in to the site; it only opens the admin console's own password sign-in.
  2. Find Admin in the account menu. Its Overview shows the server's load, and Updates says whether it's up to date.
  3. To update from there with one button later, turn on the updater.

On a machine with 1 GB of memory, add the small-VPS preset first: cat ops/web/small-vps.env >> ops/web/.env. It lowers the limits to what one CPU keeps responsive. See Small VPS.

Behind your own reverse proxy

If the machine already runs Traefik, nginx, Nginx Proxy Manager, Caddy or SWAG, let it keep ports 80 and 443 and the certificates. Playmat's web container stays (it routes the game connection and card pictures), but serves plain HTTP on its port 80 and publishes nothing on the host.

# in ops/web/.env
DOMAIN=play.example.com      # the name your proxy serves
TLS_MODE=external
PROXY_NETWORK=proxy          # the Docker network your proxy is on

# start it with the proxy override
docker compose -f ops/web/docker-compose.yml -f ops/web/docker-compose.proxy.yml --env-file ops/web/.env up -d

Then point your proxy at http://playmat:80 on that network, with WebSocket upgrades allowed on /ws (the game connection) and a long read timeout so idle games aren't cut off:

  • Traefik: nothing to write. The override carries the labels; set TRAEFIK_ENTRYPOINT and TRAEFIK_CERTRESOLVER in .env to your entrypoint and resolver names.
  • Nginx Proxy Manager: a proxy host for your domain, forward to http, playmat, port 80, with Websockets Support on and a certificate on the SSL tab.
  • nginx, SWAG, Caddy: ready-made configs are in the README.

The game server only accepts browsers from https:// plus DOMAIN. If players use another port or name, set XMAGE_ALLOWED_ORIGINS and XMAGE_PUBLIC_URL to the address they open. Keep TLS_MODE=external in .env: the Update button reads it to keep using the override.

Questions

How big does the card picture cache get?

The imgcache service keeps every picture players have looked at, so it grows with use. It's capped at 20 GB (IMGCACHE_IMAGES_MAX_SIZE); once full, the pictures used least recently are dropped first, and so is any picture nobody has looked at in a year. Scryfall lookups have their own 1 GB cap (IMGCACHE_API_MAX_SIZE). A playgroup's server usually stays far below that. Pictures are only downloaded as cards are shown, unless you fill the cache ahead of time with warm-images.mjs.

Can the server take card pictures from my own Scryfall mirror?

Yes. Point the image cache at it in .env and run up -d:

# in ops/web/.env
IMGCACHE_CARDS_UPSTREAM=http://192.168.1.50:8000/cards   # your mirror's pictures
IMGCACHE_FALLBACK=on                                     # Scryfall fills what it lacks

The mirror serves pictures in Scryfall's CDN layout (/normal/front/7/6/<id>.jpg). Plain http:// works for a mirror on your LAN. With IMGCACHE_FALLBACK=on, anything the mirror lacks comes from Scryfall. If your mirror also answers Scryfall's API, set IMGCACHE_API_UPSTREAM too; otherwise card lookups stay on Scryfall, cached for a day. The full list of what the mirror has to serve is in the README.

What is XMAGE_GATEWAY?

The game server is being rewritten in Rust a piece at a time. The first piece is a small gateway that sits in front of the Java server and takes the game connections. It sends players the same messages but makes the game-state updates itself, which takes work off Java. XMAGE_GATEWAY=on in .env turns it on, then run up -d. If the gateway stops, Caddy sends players straight to the Java server until it's back. It's off by default while it's new. With it on, card lookups, card search, deck checks, deck sync, deck imports by link, parts of the staff console, support's records and most of the Career can be answered in Rust too (XMAGE_ROUTE_CATALOG, XMAGE_ROUTE_ACCOUNT, XMAGE_ROUTE_DECKIMPORT, XMAGE_ROUTE_ACCESS, XMAGE_ROUTE_STAFF, XMAGE_ROUTE_ADMIN, XMAGE_ROUTE_ACCOUNTS, XMAGE_ROUTE_SUPPORT, XMAGE_ROUTE_CAREER, XMAGE_ROUTE_CAREERPROGRESS, which also covers quests and the capsule shop); they stay with Java unless you set them. XMAGE_ROUTE_CAREERPAYOUTS moves what a finished game pays in the Career: shadow has Java pay and the gateway check each payout against its own, and rust has the gateway pay duels and games outside the Career's tables. Setting it back to java is safe: Java pays anything left waiting the next time it starts. XMAGE_SHADOW_USERS limits shadow to a few accounts while you try it. The gateway keeps its shadow and hosted-game counts across updates in saved/gateway-totals.json (XMAGE_GATEWAY_TOTALS), by day, so a week of them can be read from /totals on port 17180 even after a deploy. Details are in the README.

What is XMAGE_AI_BACKEND?

A new AI written in Rust can play against people instead of the Java AI. It decides in milliseconds instead of seconds. Java still runs the game, and if the new AI ever loses track of it, the Java AI takes over for the rest of that game. XMAGE_AI_BACKEND=rust turns it on for the players listed in XMAGE_RUST_AI_USERS (user names separated by commas, or * for everyone), then run up -d. It only plays one-on-one games whose cards are all verified against Java (10,612 cards for now, from the Career, meta and starter decks and a wider share of the Pioneer pool; the server log names the cards that aren't). XMAGE_ENGINE=java turns it off again. While it plays, it also checks the screens it would draw against Java's (every 10th question by default, XMAGE_RUST_VIEWS_EVERY; 0 turns that off), and its prompts and game log at every question (XMAGE_RUST_PROMPTS=0 turns that off); the admin console's Overview shows how many matched. Details are in the README.

What is PLAYMAT_AI_POLICY?

It picks how the Rust AI decides, both when it plays against people in Java's games and in games the Rust engine hosts. Leave it at playouts, the default. mcts searches with several threads (up to 4, PLAYMAT_AI_THREADS): in our benchmarks it's no stronger and uses far more CPU, so it's only worth trying on a machine with cores to spare. quick doesn't search at all and is the weakest; random plays random moves. Set it, then run up -d. Details are in docs/rust/Ai.md.

What is XMAGE_RUST_HOST_USERS?

It lets the Rust engine play whole games, with no Java game behind them. It's new and still being tried, so it's off by default. It needs the gateway (XMAGE_GATEWAY=on). List the players whose games it should host (user names separated by commas, or * for everyone), then run up -d. It only hosts one-on-one games, against the AI or between two people, outside the Career and outside tournaments and drafts, whose cards are all verified against Java; other games play on Java as before. A game between people is hosted when both players are listed (or opted in) and connected through the same gateway. In a best-of-three, each game is hosted on its own and Java keeps the score and the sideboarding. The table's priority timer works as on Java: each game of a match keeps the time left from the earlier ones, and a player whose time runs out loses the match. The table's starting life, free mulligans, AI skill and rollbacks are played; a table set up some other way (another mulligan, a hand size other than 7, a companion) stays on Java. These games pay the Career like any other, show up in History when replays are on, and can be watched. Against the AI, the solo tools work on them too: saves, "Try this turn again", advice and the practice tools. A save made on the Rust engine can only be resumed while the Rust engine is on. XMAGE_ENGINE=java turns it off. The gateway's /metrics counts hosted games and how they ended (playmat_gateway_host_games_ended_total). Each hosted game also leaves a record in saved/host-games (the last 500, XMAGE_RUST_HOST_RECORDS_KEEP), so a game a player reports can be played again exactly. Details are in the README.

Can players turn the Rust engine on themselves?

Yes, with XMAGE_RUST_OPT_IN=on (it also needs XMAGE_GATEWAY=on). Each player then gets a "Play on the Rust engine" switch in Settings → Gameplay, off until they turn it on. Their games that qualify, the same ones as above, are played by the Rust engine; the rest stay on Java. A game on the Rust engine shows a "Rust engine" chip on the board and a short note as it starts. The players listed in XMAGE_RUST_HOST_USERS keep it on whatever their switch says.

Can the XMage desktop client connect?

No. Playmat servers speak only to the web client (and the Android and desktop apps, which are the web client). The desktop client's protocol was removed to make the move to Rust possible.

From ghcr.io/arcanite24/playmat-server and ghcr.io/arcanite24/playmat-web, built from github.com/arcanite24/playmat. Other copies of the repository on GitHub aren't ours: don't take images, installers or install commands from them.

Sign in with an identity provider

Players can sign in through an identity provider (OpenID Connect) instead of a password: Pocket ID, Keycloak, Authentik, or any provider that publishes a discovery document. In ops/web/.env, set the client's details, with the callback URL https://YOURDOMAIN/auth/oidc:

XMAGE_OIDC_DISCOVERY=https://id.example.com/.well-known/openid-configuration
XMAGE_OIDC_CLIENT_ID=playmat
XMAGE_OIDC_CLIENT_SECRET=...
XMAGE_OIDC_LABEL=Pocket ID

With XMAGE_AUTH=true and the three set, the sign-in screen offers the provider as a button named by XMAGE_OIDC_LABEL (empty: "OIDC"). The first sign-in makes the player an account here, named after the provider's display name and with its verified email, and the player's device is remembered: from then on it signs in without a password.

Two things to know before you switch it on. The server talks to the provider directly, so your container must be able to reach the discovery URL; when the provider sits behind a proxy, that can be a different address than the players' one. And a player whose provider email isn't confirmed yet is told to confirm it in the provider. An existing account here with the same email is signed in to only once it has confirmed that address in Settings; until then the player is asked to confirm it first.

Signing a player out also ends the provider's session where the provider advertises RP-initiated logout in its discovery document, so the next click of the button asks for the passkey again - whether the sign-in came through the provider or is a reload of one. Without it, or for an account that never signed in through the provider, signing out is unchanged.

XMAGE_OIDC_ADMIN_GROUP names a user group in the provider: a member who signs in opens the admin console on their own session, with no password, for as long as that session lives, and it returns when they sign out. While it lasts the member is a full owner, the same envelope the shared admin password already gives; XMAGE_ADMIN_PASSWORD stays the break-glass. Don't restrict the client to that group in the provider, or everyone outside it is denied sign-in.

Pocket ID is a selfhosted, passkey-only provider and the one to start from: how to add the client, what its passkeys mean for players, key rotation, and its one algorithm it can't use, are in the deployment guide.

The provider as the only sign-in

XMAGE_OIDC_ONLY=true makes the provider the only way to get in. It refuses signing in with a typed password (web and desktop clients alike), creating an account (including through an invite), resetting a forgotten password, and Sign in with GitHub.

What keeps working: signing in with the provider, signing in on a remembered device, reconnecting a game in progress, asking for access on a contributors server, and the admin console — staff are never locked out.

Use it only when your players sign in from a browser. The classic desktop client and the sideloaded Android app can't sign in on such a server (the released Playmat desktop app is fine: it ships the web client). Set XMAGE_DESKTOP=false on a web-only server. While the provider is down, no new sign-in works, but remembered devices and games in progress are unaffected. A player who is locked out gets a reset code from the admin console, or you turn the flag off until they're in.

Building the images yourself

To run your own changes, empty XMAGE_SERVER_IMAGE and XMAGE_WEB_IMAGE in .env and start with up -d --build. The first build compiles every card and takes tens of minutes; it needs more than 1 GB of memory.
